# 多账号权限及数据库改造方案

日期：2026-11-03，修订 0.3。业务及技术文档已验收通过，本稿补明确三项非阻断要求；未建表、未修改正式代码。权限矩阵见[PRD](02-案卷Windows本地多人版PRD.md)及[角色权限矩阵](角色权限矩阵.md)。

## 1. 已证实的改造起点

`verifyLoginCredentials()` 用 env 的 `ANJIAN_USER/ANJIAN_PASS_HASH`；`createSession()` 的 sessions 记录没有用户关联；`apiAuth()` 信任 `X-Anjian-Actor`；静态 token 可通过 `anjian_token` cookie 进入业务 API；`internalAuth()` 是另一条密钥入口。Electron 每次生成 internal key 并限制其路径，但这仍不等于多用户权限。[A02–A04、A15]

现有 scrypt、登录限速、HTTP-only Cookie、WAL、外键、`withImmediateTransaction()`、`withChangeContext()`、change_log 触发器均有复用价值。需要避免把单账号 Session 和 actor 文本继续当作授权依据。[A02–A05]

## 2. 建议模型（字段为设计，非已存在）

| 对象 | 建议字段/约束 | 原因 |
|---|---|---|
| users | `id TEXT PK`（UUID）、`username`、`username_normalized UNIQUE`、`display_name`、`password_hash`、`role_key`、`active`、`session_version`、`version`、UTC 创建/修改时间 | 稳定身份、唯一用户名、停用、乐观锁；不硬删除用户 |
| sessions | 用户外键、随机 token 摘要、登录时 session_version、创建/失效/最后活动时间 | 服务端校验；数据库泄露时减少可直接重放的会话材料 |
| role catalog | 代码内固定 `admin/editor/viewer` 和权限键映射 | 最小充分设计；首版不建立可编辑角色/权限关系表 |
| audit_log 扩展 | `actor_user_id`、显示名快照、actor_kind、request_id、脱敏结构化摘要 | 不把历史文本 actor 错归给新账号；人与系统操作分开 |
| change_context/change_log 扩展 | 稳定 actor ID、触发 request_id、系统派生关联 | 保留现有旧/新值追溯与 append-only 保护 |
| 可写业务表 | `version INTEGER NOT NULL DEFAULT 1` | 统一乐观锁；首版不加案件软删除或文件隔离模型 |
| 精简律师费 | 约定金额、折扣、折扣后金额、付款状态、备注及版本；金额使用分单位 | 全部启用账号读取；管理员/编辑修改；不把折扣挂在分账比例上 |
| reminder_deliveries（账号投递） | 真实 user_id、reminder_id、reminder_version、channel 及投递状态；去重键包含账号 | 来源共享，但各账号投递记录独立；不能只按提醒/通道全局去重 |
| reminder_receipts | 与账号投递关联且 user_id 一致，received_at、shown_at、read_at 分别记录 | 展示、已读不能使用其他账号或一条全局 delivery 的状态 |
| 备份 manifest | backup_id、应用/上游/schema 版本、文件相对路径/大小/摘要、对象数量、完成标记 | DB 与文件成套验证，不依赖电脑绝对路径 |

用户名规范建议限制长度、去首尾空白、ASCII 大小写无关，并明确 Unicode 规范化规则；提交前展示最终登录名，不允许规范化后重名。密码不做同样的规范化。密码哈希复用案齐 `scrypt-v1` 与 legacy 校验，新创建/重置只生成当前格式，不为借鉴 LawLink 另外引入 bcrypt。[A04、L01–L02]

保留 `events.created_by` 的既有来源枚举 manual/llm/import；另设用户字段或通过审计关联实际账号，避免破坏已有校验。已有业务主键先保留，未来数据库迁移必须维护映射，不因预留云端重写全部 ID。[A20]

## 3. 初始化与迁移

推荐迁移顺序：先停写/保留旧版本及完整目录副本，在虚构旧库演练；跑原有上游迁移，再跑派生项目迁移；事务内建用户/会话字段及约束，验证数量/外键/审计；成功后才切换应用配置。首次管理员创建使用事务内的一次性初始化状态/唯一约束，不能只靠先查询用户数。[A03]

全新安装从 GUI 创建管理员。对既有单账号数据，建议由使用者完成原有凭据验证后明确确认导入该账号为首位管理员，只导入合法哈希，不导出密码；清除旧 Session、停用原 env 登录回退和静态 Token 入口。不能在“迁移成功”后留下绕过 users.active 的旧路径，也不能仅凭能读本机 config 就授予新管理员。未来开发时先在副本演练，不自动迁移未知真实目录。

历史 `web/cli/internal/system` actor 保留原文并标为历史未知用户，不回填成新管理员。旧会话无法可靠对应独立账号，统一失效并要求重新登录。改密、停用、改角色及重置密码在同一事务内更新版本、撤销会话并写审计；保护最后一位启用管理员且防并发穿透。管理员忘记密码的恢复流程需凭本机明确操作恢复管理员身份并撤销会话，不提供隐藏默认密码。

上游目前使用递增 `PRAGMA user_version`，迁移至 032。直接把本地迁移命名为 033 会与以后上游冲突。建议保留上游迁移器，新增很小的派生迁移目录与独立 `local_schema_migrations(id,checksum,applied_at)`：先上游后派生，已应用脚本内容不允许被静默替换。升级时先验证上游版本兼容范围和迁移文件散列，遇到上游 schema 冲突停止。该低侵入技术设计随 Phase 0 文档审阅通过，实施仍需对应阶段计划确认；不引入 ORM 或全面数据库抽象。[A03]

回滚以“旧程序 + 升级前整套数据库/文件/必要配置”恢复，不能让旧程序打开已升级的新库冒充回滚。正式改动前的最小备份和可恢复演练是 Phase 1 前置门槛，完整 GUI 统一备份在 Phase 4 完成。

## 4. 认证、授权和请求边界

统一流程建议：解析 Session → 校验有效期、user.active、session_version → 建立不可变 `req.user` → 权限键检查 → 输入/版本校验 → 事务修改和审计 → 返回结果。`req.actor` 仅由服务端派生，外部 `X-Anjian-Actor` 不参与身份或审计归属。

所有可写入口显式登记权限，新增未分类端点默认拒绝；不只检查 HTTP 方法。`GET /reminders` 会调用 syncCase，证明 GET 也可能维护数据库；建议将其派生维护放在系统 worker，或明确以 system 身份执行必要幂等维护，不能让只读用户获得通用写能力。[A12]

静态 Token、internal、AI Agent、LegalRAG、IM 及复杂财务/分账/结算首版关闭并在服务端拒绝，管理员也不例外；保留代码、测试和历史数据。精简律师费使用 fees.read/fees.write 独立白名单，不把旧 fees Router 整体放开。未来确有自动化需求再增加独立服务身份、范围和撤销机制，桌面子进程不能自动取得管理员权限。

本地服务只监听回环，Cookie 使用 HttpOnly/SameSite；仍需写请求 Origin/Host 校验及 CSRF 防护，不能认为回环自动安全。上传使用 raw body，普通 JSON 前端包装器不能覆盖它；SSE 和文件流须在建立连接时鉴权，并在停用/权限变更/退出时终止或短周期复核，已建立的流不能无限延续权限。[A02、A10、A12、A15]

全部 131 条显式声明见[接口权限清单](接口权限清单.md)。这是静态清单，不是运行时覆盖证明；Phase 2 需对实际 Express 挂载、路由工厂、隐式 HEAD、静态文件、错误路径和未来新增入口作比对。GET 隐式 HEAD 不能绕过读取授权；静态前端可公开登录资源，案件文件不得通过静态目录裸露。

### 4.1 通知读取与状态修改的账号隔离

共享案件/提醒源不意味着共享个人通知记录。`notifications.self.read` 覆盖本人列表、投递历史/详情和 SSE；`notifications.self` 覆盖本人的展示确认及已读。两者的 user_id 均取自服务端有效会话，不取请求头、查询参数或 body 中的用户标识。

查询和更新必须同时约束对象 ID 与会话 user_id，不能先按 deliveryId 查询再相信客户端声明的所属用户。SSE 首次队列补发和后续广播都筛选真实接收账号；停用/会话撤销后关闭流。账号级投递去重、展示和已读互不影响；旧全局投递不能被直接视为任一新账号的个人记录。管理员使用普通通知接口也只能处理本人通知，另行授权的全量审计不改变此规则。Phase 2 增加伪造账号参数、跨账号 ID、流式泄露和共享状态串用的负向验收。

### 4.2 普通界面需要的最小系统配置

Phase 2 逐页核查原生前端对 `/api/settings`、元数据和通知状态的读取依赖，记录调用位置、实际必需字段及编辑/只读体验。完整 `GET/PUT /api/settings` 仍要求 `system.manage`，不得通过降低该接口权限维持旧界面。

确有依赖时，以 `ui.config.read` 提供服务端固定白名单的最小脱敏配置，优先复用已具安全投影的元数据/状态接口；具体字段由依赖核查确定，不先开放通用 key 查询或全表 settings 透传。只返回核心界面必要的开关/展示值；不含密码/哈希、Token、密钥、供应商凭据、内部绝对路径、原始错误日志或关闭模块管理配置。客户端不能通过 keys/user_id 等参数扩大返回范围；配置写入仍仅管理员。验收同时覆盖核心界面可用性、越界字段拒绝与完整设置访问拒绝。

## 5. 并发、幂等和审计

普通案件 PATCH 当前 `UPDATE ... WHERE id=?`，即使包在事务内也会覆盖过期客户端的值。全部核心可写表采用 `UPDATE ... WHERE id=? AND version=?` 并检查变更行数，成功后 version+1；范围内普通记录删除、附件解除引用同样核对版本，案件软删除/文件本体删除及对象恢复暂缓。事务内重新读依赖状态，冲突返回 409。SQLite 同步连接的事务回调不放 await，异步文件处理前后的身份、案件状态和版本须重新确认。[A03、A06]

事件改变会派生期限和任务，应把来源更新、重算、版本递增、change_log 和 audit 放在同一事务。预览返回涉及对象版本，确认时复核；普通更新与批量更新、快速录入、收件箱 accept 和撤销完成状态均须遵守同一规则。只给案件表加 version 不够。[A07、A09]

幂等键优先用于创建案件/事件、上传登记、批量动作和备份恢复启动：绑定 user_id、操作类型、请求摘要、有限保留期；同键同内容返回原结果，同键不同内容拒绝；结果不明先查状态再重试。普通版本更新可利用 version 阻止重放，但不得让重试重复派生任务。

修改及其审计同事务提交；文件动作通过准备/提交/补偿状态关联审计。账号只停用不硬删，记录当时显示名与 user_id；禁止将密码/hash/token/密钥/文件正文放入审计。登录失败、授权拒绝等事件单独记录脱敏运行安全日志，不能与业务成功混淆。LawLink 普通 audit 的吞错行为不符合“所有修改必须留痕”，应参考 auditTx。[L07]

## 6. 文件和数据库一致性

现有上传先写文件，随后独立 INSERT attachments 和 audit；若登记失败，可能留下未登记文件，不能因 writeUniqueSecureFile 的路径保护就判定跨文件/数据库一致性已解决。[A10–A11]

建议保留原相对路径与同名独占写：先写应用暂存区并 fsync，记录准备状态；同卷安全转入目标目录，事务登记附件/关联/审计，失败按文件身份补偿；崩溃重启对准备状态做核对，不删除未知文件。存储文件不能直接接受客户端绝对路径；事件/期限/费用/worklog 引用必须属于同案，不存在的对象拒绝。新文件大小、摘要及存储键入库，原始显示名单独保留。

首版不提供案件软删除、文件本体删除、应用隔离区及对象恢复；不新增对应 API 或 UI，遗留端点如能间接执行上述行为也须拒绝。解除附件引用只移除关联并留审计，原件及历史数据保留。统一数据库/文件备份恢复继续纳入首版，两种恢复范围不得混淆。

Windows 名称还须拒绝保留设备名、冒号/ADS、结尾空格或点、盘符/UNC/绝对路径、大小写碰撞，并核对 junction/reparse point 与长路径。保留现有 realpath/文件身份保护，不为“兼容 Windows”删除关键检查。本轮纯函数探针已证实 `CON`、`NUL`、`a:b`、`test.` 和 `file:stream.pdf` 会通过现有名称函数；尚未声称已利用这些名称突破目录。[A11、T02]

## 7. 精简律师费与历史兼容

上游 `fees.js` 的概览/明细会组合分账信息，PATCH 在金额或付款状态变化时会查询结算上下文；遇受保护历史会返回 `settlement_preview_required`。因此不采用“只隐藏分账按钮，再放行全部 fees API”的方案。[A22]

首版仅开放约定金额、折扣、折后金额、付款状态、备注的读取和新建/修改。优先复用 `fee_items`、分单位金额解析和版本控制，增加最少必要字段或独立补充表，使用简单费用读写服务过滤响应与请求；不调用分账分配、结算确认、发票和凭证管理流程。具体字段落点在 Phase 2 开始时提供迁移方案，不在 Phase 0 改库。

历史记录原金额不回算成未曾记录的约定金额，缺失折扣不伪造。复杂财务表、历史分账和结算记录原样保留且关闭管理接口；已结算或存在复杂保护的费用不绕过上游约束直接改写，应明确提示历史保护并报告处理边界。范围内新建的简单费用不应因为关闭复杂模块而无法管理。折扣单位/精度、舍入、付款枚举和受保护历史的展示/编辑映射需在 Phase 2 前确认，不扩展已确认的五项业务范围。

全部启用账号通过 `fees.read` 读取，管理员/编辑通过 `fees.write` 新建/修改；只读不写。每次金额、折扣、付款状态或备注变更都核对版本、写真实账号审计，事务失败回滚。服务端校验折后金额与规则一致，不能信任客户端计算结果。精简费用记录删除本轮没有新增授权，先不开放；复杂费用 DELETE 与凭证接口关闭。

## 8. 验收门槛

用虚构账号和测试库验证：停用/改密/改角色撤销；最后管理员竞态；header 假冒；全部接口三角色直调；跨案附件引用；并发编辑与重算；重复请求；DB/文件任一步骤故障回滚；审计失败不得返回业务成功。现有 scrypt 和原有单账号测试保留并扩展，不能删去旧安全断言换取通过。完整数据库及 API 测试本轮未运行，见验证记录。
